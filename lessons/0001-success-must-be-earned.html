SSSF · Lesson 01

Success Must Be Earned

The phase primitive, and the one line of Python that makes agent runs repeatable.

Mission item you are attacking today: "Explain, without notes, why a phase defaults to fail and what flips it." Everything else in SSSF sits on top of this.

The problem this solves

An agent will tell you it succeeded. It will say so in prose, confidently, whether or not it did. If your workflow treats "the agent finished talking" as "the step passed," your pipeline is a random number generator with good manners.

SSSF's answer: the agent never decides. Deterministic Python owns sequencing, retries, and acceptance; agents are bounded nodes inside that graph. The repo's phrase for it is agent proposes, code disposes.overview

One primitive, three lanes

Every ADW run is a sequence of phases. There is exactly one way to open one:

with run.phase(PhaseParams(...)) as ph:
    ...

Three kinds, and the kind is just a label saying who owns the work:

KindOwnerWhat happens inside
engineerthe humanph.log(input=...) — capture the ask
agentan agent nameph.call(AgentCall(...)) — prompt in, typed envelope out, gates verified
codegit, etc.deterministic steps: branch, commit, migrate

The rule that keeps traces honest: a code step never hides inside an agent phase. If git committed, there is a phase that says so.

The mechanic

Open adws/adw_modules/runner.py and read Run.phase. It is a context manager, and the whole design is in its try/except/else:

try:
    yield PhaseHandle(self, phase)
except BaseException as error:
    phase.status = "fail"          # success must be earned
    ...
    raise
else:
    phase.status = "success"

Note where the statuses come from. Phase.status is declared "fail" at construction in data_types.py, before the body ever runs. Nothing inside the with block can announce success. The only thing that flips it is exiting the block cleanly — reaching the end without raising.

So the contract inverts the usual one. You do not report failure. You fail to report success.

Agent phases carry two extra conditions. A clean exit is necessary but not sufficient. Inside ph.call, the agent's final JSON must parse against the declared output type, and every gate must come back green. Either one failing raises — which lands you in the except branch, which is already fail. retries=N buys extra gate-correction rounds through the same session before that raise.

Phase success is not run success

These are different questions, deliberately. Run.finish() takes two criteria:

phases_ok = bool(self.phases) and all(p.status == "success" for p in self.phases)
ok = phases_ok and accepted

A test phase that ran the suite did its job even when the suite came back red. The phase succeeded. The run must not. The docstring in runner.py records a real bug from before this split existed: runs were written green to the db and the terminal while exiting 1, so every human reading the trace saw success and only CI saw the truth.

Retrieval

Answer from memory before scrolling to check. Getting these wrong is how they stick.

1. A code phase runs git commit, which exits non-zero and raises. What is the recorded phase status?

2. An agent phase exits cleanly, envelope parses, one gate reports red. Status?

3. Every phase succeeded, but the test suite the test phase ran came back red. Exit code?

Free recall

In two sentences: why does Phase.status default to fail rather than being set to fail when something goes wrong?

Because setting failure on error assumes you can enumerate every way a step can go wrong, and you cannot — a crash, a timeout, or a kill leaves the status wherever it was. Defaulting to fail means any path that does not reach a clean exit is recorded as failure, so an unhandled case degrades to honest instead of to a false green.
